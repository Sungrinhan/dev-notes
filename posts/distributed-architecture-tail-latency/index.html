아키텍처 스타일 시리즈 2편

분산 아키텍처 5가지 스타일과 꼬리 지연: p99로 본 서비스 분리의 비용

서비스 기반, 이벤트 드리븐, 스페이스 기반, 오케스트레이션 SOA, 마이크로서비스의 장단점을 비교하고, TypeScript 시뮬레이션으로 서비스 수에 따라 p99 꼬리 지연이 커지는 과정을 확인한 학습 노트입니다.

By HanSungLin · 2026-11-25 · 10 min read · 2044 words

모놀리식 애플리케이션을 여러 서비스로 나누면 내부 함수 호출이 네트워크 요청으로 바뀐다. 그 순간 지연과 실패라는 비용이 생긴다. 수강 중인 온라인 소프트웨어 아키텍처 강의에서 이번 수업은 분산 아키텍처의 다섯 가지 스타일을 비교하고, 서비스를 여러 번 거칠수록 느린 요청이 늘어나는 꼬리 지연을 시뮬레이션으로 확인했다. 수업 실습은 파이썬이었는데, 나는 TypeScript로 옮겨 직접 돌렸다. 그 결과 서비스마다 느린 호출 확률이 1%뿐인데도 10개 서비스를 거치면 요청의 9.6%가 느린 호출을 한 번 이상 만났다. 이 글은 그 결과와 스타일 선택 기준을 정리한 학습 노트다.

핵심 요약

  • 분산은 확장을 쉽게 해 주는 대신 함수 호출을 네트워크 호출로 바꾼다. 네트워크가 믿을 만하고 지연이 없다는 가정은 분산 컴퓨팅의 대표적인 오류다.
  • 서비스 기반, 이벤트 드리븐, 스페이스 기반, 오케스트레이션 SOA, 마이크로서비스는 각자 다른 품질을 얻고 다른 비용을 낸다.
  • 스타일은 확장성, 성능 같은 품질 요구사항 중 설계를 이끄는 소수의 드라이빙 특성을 먼저 정한 뒤 고른다.
  • 각 서비스가 빨라도 여러 서비스를 거치면 느린 호출을 만날 확률이 쌓인다. 내 시뮬레이션에서 p99는 서비스 1개일 때 17.5ms, 10개일 때 299ms였다. p99는 고르게 늘지 않고 계단처럼 뛰는데, 평균만 봐서는 이 변화가 잘 안 보인다.
  • 전부 나누기보다 연말에 트래픽이 몰리는 주문 도메인처럼 꼭 필요한 부분만 떼어 내는 접근이 현실적이다.

분산 아키텍처는 왜 필요하고 무엇을 대가로 내나

분산 아키텍처는 애플리케이션을 여러 배포 단위로 나누고 네트워크로 연결하는 구조다. 시리즈 1편에서 다룬 모놀리식은 배포 단위가 하나라서, 트래픽이 늘면 전체를 통째로 복제해 확장해야 한다. 주문 화면만 붐벼도 카탈로그와 리뷰 코드까지 같이 늘어난다.

앱을 나누면 필요한 부분만 키울 수 있다. 대신 프로세스 안의 함수 호출이던 것이 네트워크 요청이 된다. 함수 호출은 거의 실패하지 않고 지연도 일정하지만, 네트워크 요청은 느려지고, 끊기고, 가끔 아예 응답이 없다.

분산 컴퓨팅에서 피해야 할 여덟 가지 가정

분산 시스템을 설계할 때 흔히 빠지는 잘못된 가정을 정리한 목록이 있다. 분산 컴퓨팅의 오류(Fallacies of distributed computing)는 1994년 썬 마이크로시스템즈의 L. Peter Deutsch가 일곱 가지로 정리했고, 1997년 무렵 James Gosling이 여덟 번째를 더했다.

  1. 네트워크는 안정적이다.
  2. 지연은 0이다.
  3. 대역폭은 무한하다.
  4. 네트워크는 안전하다.
  5. 토폴로지는 바뀌지 않는다.
  6. 관리자는 한 명이다.
  7. 전송 비용은 0이다.
  8. 네트워크는 균일하다.

수업에서 강조한 건 앞의 두 가지였다. 네트워크가 늘 성공하고 즉시 응답한다고 가정하면, 서비스 하나의 일시적인 지연이 전체 요청을 붙잡는 상황을 설계 단계에서 놓친다. 뒤에서 볼 꼬리 지연이 바로 두 번째 가정이 깨진 결과다.

분산 아키텍처 5가지 스타일 비교

마크 리처즈와 닐 포드의 『Fundamentals of Software Architecture』(O'Reilly)(국내판 『소프트웨어 아키텍처 101』)은 분산 스타일을 아래처럼 나눈다. 수업도 같은 분류를 따랐다.

스타일 핵심 구조 얻는 것 내는 비용
서비스 기반 큰 단위 서비스 몇 개가 데이터베이스 하나를 공유 트랜잭션 처리가 쉽고 도입이 단순함 스키마 변경이 여러 서비스에 번짐
이벤트 드리븐 서비스가 비동기 이벤트를 주고받음 응답성, 확장성 이벤트 순서와 실패 처리가 어려움
스페이스 기반 데이터를 메모리 격자에 두고 처리 DB 병목 감소, 급격한 트래픽에 강함 구조가 복잡하고 메모리 비용이 큼
오케스트레이션 SOA ESB가 서비스 호출을 중앙에서 조율 서비스 재사용 중앙 집중으로 결합도가 커짐
마이크로서비스 서비스마다 데이터베이스를 따로 둠 독립 배포와 확장 운영 복잡도, 네트워크 호출 비용

서비스 기반 아키텍처

서비스 기반 아키텍처는 애플리케이션을 주문, 회원, 카탈로그처럼 큰 단위 서비스로 나누고(리처즈와 포드는 보통 4~12개 정도로 본다) 데이터베이스는 하나를 같이 쓴다. 같은 DB를 쓰니 주문과 재고를 한 트랜잭션으로 묶기 쉽다. 반면 테이블 하나를 바꾸면 그 테이블을 읽는 서비스를 모두 확인해야 한다. 분산으로 가는 첫 단계로 고르기 좋은 스타일이다.

이벤트 드리븐 아키텍처

이벤트 드리븐은 서비스가 서로를 직접 부르지 않고 "주문 생성됨" 같은 이벤트를 발행하고 구독한다. 주문 서비스는 이벤트만 던지고 바로 응답하므로 사용자가 기다리는 시간이 짧다. 대신 이벤트가 순서대로 도착한다는 보장이 약하고, 중간에 실패한 처리를 되돌리기 어렵다. 마틴 파울러는 「What do you mean by "Event-Driven"?」에서 같은 이름 아래 서로 다른 패턴들이 섞여 있다고 짚는데, 설계 전에 어떤 의미의 이벤트 드리븐인지 팀이 합의해 두는 게 좋겠다고 느꼈다.

스페이스 기반 아키텍처

스페이스 기반 아키텍처는 처리 단위마다 데이터를 메모리에 복제해 두고, 데이터베이스에는 비동기로 나중에 반영한다. 요청이 DB를 거치지 않으니 티켓 오픈이나 한정 판매처럼 순간 트래픽이 몰리는 곳에서 DB 병목을 줄인다. 그만큼 메모리 비용이 크고, 복제와 동기화 구조를 이해하고 운영하기가 어렵다.

오케스트레이션 기반 SOA

오케스트레이션 기반 SOA는 ESB(엔터프라이즈 서비스 버스)가 서비스 호출을 중앙에서 조율하며 재사용을 추구했다. 재사용을 위해 공통 서비스를 많이 만들수록 모든 흐름이 ESB와 공통 서비스에 묶였다. 결과적으로 한 곳을 바꾸면 여러 업무 흐름이 함께 흔들리는 높은 결합도가 남았다. 수업에서는 이 스타일을 "재사용이 결합을 만든 사례"로 소개했다.

마이크로서비스

마이크로서비스는 서비스마다 데이터베이스를 따로 두어 독립적으로 배포하고 확장한다. 제임스 루이스와 마틴 파울러의 「Microservices」는 각 서비스가 자기 데이터를 관리하는 분산 데이터 관리를 특징으로 꼽는다. 독립성이 큰 만큼 서비스 수만큼 배포 파이프라인, 모니터링, 장애 대응이 늘고, 서비스 사이의 호출은 전부 네트워크를 탄다.

품질 요구사항으로 스타일을 고르는 법

스타일 선택의 출발점은 품질 요구사항이다. 확장성, 탄력성, 성능, 가용성, 단순함, 비용 같은 특성은 서로 맞바꾸는 관계에 있다. 단순하고 싼 구조를 원하면 확장성과 탄력성을 덜 얻고, 확장성과 탄력성을 원하면 복잡도와 비용을 더 낸다.

그래서 수업은 모든 특성을 다 챙기려 하지 말고, 설계를 이끄는 소수의 드라이빙 특성을 먼저 고르라고 했다. 『Fundamentals of Software Architecture』에서 리처즈와 포드는 이를 아키텍처 특성 중 몇 개만 우선순위로 정하는 일로 설명한다. 서점이라면 이런 식이다.

  • 평소엔 조용하고 연말에만 주문이 몰린다: 탄력성이 드라이빙 특성이다. 주문만 따로 늘릴 수 있는 구조가 필요하다.
  • 팀이 작고 기능이 자주 바뀐다: 단순함과 변경 속도가 우선이다. 모놀리스나 서비스 기반이 맞다.
  • 결제와 재고가 정확히 맞아야 한다: 데이터 정합성이 우선이다. 공유 DB 트랜잭션이 가능한 서비스 기반이 유리하다.

TypeScript로 확인한 꼬리 지연

꼬리 지연은 지연 분포의 끝부분, 즉 가장 느린 소수 요청이 겪는 지연을 말한다. 보통 p99(100번 중 가장 느린 1번 정도의 지연)로 잰다. 서비스 하나는 대부분 빨라도, 요청이 여러 서비스를 거치면 그중 하나라도 느릴 확률이 쌓인다.

시뮬레이션 설정

수업의 파이썬 예제를 TypeScript로 옮겨 Node.js 24에서 직접 돌렸다. 아래에 핵심 부분만 싣고, 요청 루프와 집계까지 담은 전체 코드는 tailLatency.ts에 공개했다. 설정은 다음과 같다.

  • 서비스 호출 한 번은 99% 확률로 평균 10ms(표준편차 2ms), 1% 확률로 200ms가 걸린다.
  • 요청 하나가 서비스 1, 3, 5, 10, 20개를 순서대로 거친다.
  • 요청 10만 건을 보내고 평균, p50, p99, 그리고 느린 호출을 한 번 이상 만난 요청 비율을 잰다. Math.random()은 시드를 정할 수 없어서 작은 시드 고정 난수 생성기(mulberry32)를 넣고 시드를 42로 고정했다.
function mulberry32(seed: number): () => number {
  return () => {
    seed = (seed + 0x6d2b79f5) | 0;
    let t = Math.imul(seed ^ (seed >>> 15), 1 | seed);
    t = (t + Math.imul(t ^ (t >>> 7), 61 | t)) ^ t;
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
  };
}

const random = mulberry32(42);
const SLOW_RATE = 0.01;

// 박스-뮬러 변환으로 정규분포 값을 만든다
function gauss(mean: number, sd: number): number {
  const u = 1 - random();
  const v = random();
  return mean + sd * Math.sqrt(-2 * Math.log(u)) * Math.cos(2 * Math.PI * v);
}

function call(): number {
  if (random() < SLOW_RATE) return 200;
  return Math.max(1, gauss(10, 2));
}

function request(nServices: number): number {
  let total = 0;
  for (let i = 0; i < nServices; i++) total += call();
  return total;
}

요청 10만 건을 보내고 지연을 정렬해 p50, p99를 뽑는 부분은 이렇다. 백분위수는 보간 없이 정렬한 배열에서 해당 순위의 값을 그대로 쓴다.

function percentile(values: number[], q: number): number {
  const sorted = [...values].sort((a, b) => a - b);
  return sorted[Math.floor(sorted.length * q) - 1];
}

const totals = Array.from({ length: 100_000 }, () => request(10)); // 서비스 10개
const p99 = percentile(totals, 0.99);

결과: 평균은 고르게, p99는 계단처럼 뛴다

거친 서비스 수 평균 (ms) p50 (ms) p99 (ms) 느린 호출을 만난 요청 이론값 1 - 0.99^N
1 11.9 10.0 17.5 0.99% 1.00%
3 35.9 30.1 221.3 3.06% 2.97%
5 59.7 50.3 243.6 4.98% 4.90%
10 119.1 100.9 299.2 9.59% 9.56%
20 238.1 202.5 578.8 18.23% 18.21%

서비스 1개일 때는 느린 호출 비율이 1%에 조금 못 미쳐(0.99%) p99가 아직 빠른 쪽(17.5ms)에 걸린다. 3개만 거쳐도 느린 호출을 만난 요청이 약 3%로 늘어 p99가 221ms로 뛴다. 평균은 서비스 수에 비례해 고르게 늘 뿐이라, 평균 대시보드만 보면 이 변화를 놓친다. 느린 호출을 만난 비율은 이론값 1 - 0.99^N과 거의 같았다.

표를 자세히 보면 p99는 계단 모양으로 움직인다. 느린 호출을 한 번이라도 만날 확률이 1%를 넘는 순간(서비스 3개) p99가 느린 호출 1번 몫인 200ms대로 올라서고, 서비스 5개와 10개에서는 같은 계단 위에서 조금씩만 늘어난다. 서비스 20개에서는 느린 호출을 두 번 이상 만날 확률이 약 1.7%로 1%를 넘어서 p99가 다시 한 계단(약 580ms) 뛴다. 그래서 p99와 평균의 차이는 서비스 3개에서 크게 벌어진 뒤 한동안 비슷하게 유지된다.

같은 계산은 큰 시스템에서 더 극적이다. Jeffrey Dean과 Luiz André Barroso는 2013년 Communications of the ACM 논문 「The Tail at Scale」에서, 서버 하나가 100번 중 1번 1초 이상 걸릴 때 요청 하나가 서버 100대의 응답을 모아야 한다면 사용자 요청의 63%가 1초를 넘긴다는 예를 든다. 논문은 서버 100대에 병렬로 퍼뜨리는 구조이고 내 시뮬레이션은 서비스를 순서대로 거치는 구조라 모양은 다르지만, 1 - 0.99^100이 약 63%이듯 느린 호출을 한 번이라도 만날 확률이 쌓인다는 원리는 같다.

재시도를 더하면

수업이 연습 문제로 낸 재시도 로직도 붙여 봤다. 호출이 50ms 안에 끝나지 않으면 끊고 한 번 더 부른다. 이 시뮬레이션은 재시도가 첫 호출과 무관한 새 호출이라고 가정하므로 재시도는 거의 항상 빠르게 끝난다. 서버 과부하처럼 느림이 이어지는 상황이라면 재시도 효과는 이보다 작다. 같은 시드로 돌린 결과를 재시도 전과 나란히 놓으면 아래와 같다.

재시도 로직은 호출 함수를 감싸는 몇 줄이다.

// [걸린 시간, 호출 횟수]를 돌려준다
function callWithRetry(timeout = 50): [number, number] {
  const first = call();
  if (first <= timeout) return [first, 1];
  return [timeout + call(), 2]; // 기다린 시간 + 재시도 시간
}
거친 서비스 수 p99 재시도 없음 (ms) p99 재시도 (ms) 요청당 호출 수 (재시도)
1 17.5 17.6 1.010
3 221.3 81.8 3.031
5 243.6 104.3 5.051
10 299.2 160.3 10.100
20 578.8 302.2 20.200

재시도로 서비스 10개 기준 p99가 299.2ms에서 160.3ms로, 20개 기준 578.8ms에서 302.2ms로 줄었다. 대신 요청당 호출 수가 약 1% 늘었다. 느린 서버가 과부하 때문에 느린 상황이라면 이 추가 호출이 부하를 더 키울 수 있다. 이 시뮬레이션은 첫 요청을 끊고 다시 보내는 방식이고, 논문의 hedged request는 첫 요청을 살려 둔 채 보조 요청을 하나 더 보낸다는 점이 다르다. 「The Tail at Scale」의 hedged request가 첫 요청이 예상 지연의 95번째 백분위수를 넘길 때까지 기다렸다가 보조 요청을 보내, 추가 부하를 약 5%로 묶는 이유도 여기에 있다고 이해했다.

전부 나누지 말고 필요한 곳만 떼어 낸다

수업의 마지막 사례는 실전적이었다. 서점 전체를 마이크로서비스로 바꾸는 대신, 1편의 모듈러 모놀리스에서 연말에 트래픽이 몰리는 주문 도메인만 분리해 따로 확장한다. 모듈 경계가 이미 공개 함수로 정리돼 있다면, 그 함수 호출을 네트워크 호출로 바꾸는 범위가 주문 하나로 줄어든다.

이때 판단 기준으로 나온 개념이 아키텍처 퀀텀이다. 리처즈와 포드는 퀀텀을 독립적으로 배포할 수 있고, 기능 응집도가 높고, 정적 결합이 강하며, 동기식으로 동적 결합된 단위로 정의한다. 수업에서는 이를 확장성, 가용성 같은 특성을 독립적으로 정할 수 있는 단위로 설명했다. 주문을 떼어 냈어도 주문이 결제를 동기로 부르고 DB를 공유한다면, 둘은 여전히 함께 움직이는 한 덩어리다. 어디까지 함께 묶고 어디서 끊을지는 3편: 아키텍처 퀀텀과 서비스 입도에서 퀀텀을 직접 세어 보며 다룬다.

마틴 파울러의 MonolithFirst도 같은 방향을 말한다. 경계를 충분히 이해하기 전에 처음부터 서비스로 나누기보다, 모놀리스에서 시작해 필요한 경계를 찾아 떼어 내는 편이 안전하다는 것이다.

자주 묻는 질문

평균 지연 대신 p99를 봐야 하는 이유는 뭔가요?

평균은 소수의 느린 요청을 다수의 빠른 요청 속에 묻어 버린다. 위 시뮬레이션에서 서비스 3개일 때 평균은 35.9ms였지만 p99는 221.3ms였다. 요청 100건 중 1건이 평균의 6배 넘게 느린 셈이고, 사용자 한 명이 페이지 하나를 보며 요청을 여러 건 보내므로 그 1%를 한 번이라도 만나는 사용자 비율은 1%보다 높아진다.

이벤트 드리븐으로 바꾸면 꼬리 지연이 사라지나요?

사용자가 기다리는 경로에서 비동기로 뺀 호출은 응답 시간에서 빠진다. 다만 지연이 사라지는 건 아니고 뒤로 밀린다. 이벤트 처리가 늦어지면 알림이나 재고 반영이 늦어지고, 순서가 뒤바뀌거나 중복 처리되는 문제를 따로 다뤄야 한다.

서비스 기반과 마이크로서비스 중 무엇부터 시작해야 하나요?

드라이빙 특성이 독립 배포와 부분 확장이 아니라면 서비스 기반이 부담이 적다. 데이터베이스를 공유하니 트랜잭션과 조회가 단순하다. 특정 도메인만 독립적으로 확장해야 하는 이유가 생기면 그 도메인부터 DB를 분리해 마이크로서비스로 옮기는 식으로 나아갈 수 있다.

정리: 분산의 범위는 품질 요구사항으로 정한다

분산 아키텍처는 확장과 독립성을 주지만, 모든 호출을 실패하고 느려질 수 있는 네트워크 위에 올린다. 다섯 가지 스타일은 이 비용을 각자 다르게 나눠 진다. 그래서 스타일을 고를 때는 드라이빙 특성을 먼저 정하고, 그 특성을 얻으려고 감당할 복잡도가 어디까지인지 따져야 한다. 꼬리 지연 시뮬레이션은 그 복잡도가 숫자로 어떻게 드러나는지 보여 줬다. 서비스 하나하나가 빨라도 거치는 단계가 늘면, 느린 호출을 만날 확률이 1%를 넘는 지점마다 p99가 계단처럼 뛴다.

결국 분산 자체가 목적이 아니다. 시스템의 품질 요구사항과 감당할 수 있는 복잡도에 맞춰 나눌 범위를 정하는 게 핵심이다. 다음 편인 3편에서는 그 범위를 정하는 도구인 아키텍처 퀀텀과 서비스 입도를 유니온 파인드로 직접 계산해 본다.
