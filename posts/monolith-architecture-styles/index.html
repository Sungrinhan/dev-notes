레이어드 vs 모듈러 모놀리스 vs 마이크로커널: 쿠폰 기능 하나로 비교하기

온라인 서점에 쿠폰 할인을 추가하는 예제로 레이어드, 모듈러 모놀리스, 마이크로커널의 분할 기준과 변경 범위, 트레이드오프를 비교한 학습 노트입니다.

By HanSungLin · 2026-11-25 · 7 min read · 1581 words

같은 기능을 만들어도 코드를 어떤 기준으로 나눴느냐에 따라 고칠 파일 수가 달라진다. 수강 중인 온라인 소프트웨어 아키텍처 강의에서 이번 수업은 작은 온라인 서점에 쿠폰 할인을 붙이는 예제 하나로 레이어드, 모듈러 모놀리스, 마이크로커널을 비교했다. 강의 예제 기준으로 쿠폰을 넣을 때 레이어드는 3개 파일, 모듈러 모놀리스는 2곳(새 쿠폰 모듈과 주문 모듈의 호출부), 마이크로커널은 플러그인 파일 1개를 고쳤다. 이 글은 그 숫자가 왜 그렇게 나오는지, 그리고 숫자가 작다고 늘 좋은 건 아니라는 점을 정리한 학습 노트다.

핵심 요약

  • 아키텍처 스타일은 시스템을 큰 덩어리로 나누는 방식에 붙인 이름이다. 먼저 배포 단위가 하나인지(모놀리식) 여럿인지(분산)를 보고, 그다음 코드를 기술 역할로 나눌지 업무 영역으로 나눌지를 본다.
  • 레이어드는 기술 역할별로 층을 쌓는다. 닫힌 층은 결합도를 낮추지만, 로직 없이 층을 통과하기만 하는 아키텍처 싱크홀을 만들 수 있다.
  • 모듈러 모놀리스는 카탈로그, 주문, 쿠폰처럼 도메인별로 모듈을 나누고 공개 함수로만 소통한다. 한 프로세스 안이라 경계가 쉽게 무너지므로 규율이 필요하다.
  • 마이크로커널은 최소한의 코어에 플러그인을 끼운다. 규칙이 자주 바뀌는 기능에 강하지만, 코어와 플러그인 사이의 약속이 바뀌면 플러그인을 한꺼번에 고쳐야 한다.
  • 정답 스타일은 없다. 무엇이 자주 바뀌는지, 팀이 어떻게 나뉘는지, 기능을 탈부착해야 하는지를 보고 고르며, 섞어 쓸 수도 있다.

아키텍처 스타일은 무엇을 기준으로 나누나

아키텍처 스타일은 시스템을 큰 덩어리로 나누는 방식에 붙인 이름이다. 마크 리처즈와 닐 포드의 『소프트웨어 아키텍처 101』(Fundamentals of Software Architecture, O'Reilly)은 스타일을 두 축으로 나눈다. 첫째 축은 배포 단위다. 애플리케이션 전체를 하나로 배포하면 모놀리식이고, 여러 조각을 따로 배포해 네트워크로 연결하면 분산이다. 둘째 축은 모놀리식 안에서 코드를 자르는 기준이다.

  • 기술 분할: 화면, 비즈니스 로직, 데이터 접근처럼 기술 역할로 자른다. 레이어드가 대표적이다.
  • 도메인 분할: 카탈로그, 주문, 쿠폰처럼 업무 영역으로 자른다. 모듈러 모놀리스가 대표적이다.

수업에서는 이걸 건물에 비유했다. 같은 건물도 층으로 나눌 수 있고 칸으로 나눌 수도 있다. 소프트웨어도 같은 기능을 어느 방향으로 자르느냐에 따라 모양이 달라진다. 이번 글의 세 스타일은 모두 배포 단위가 하나인 모놀리식이고, 차이는 자르는 방향에 있다.

레이어드 아키텍처: 기술 역할로 층을 쌓는다

레이어드 아키텍처는 프레젠테이션, 비즈니스, 퍼시스턴스, 데이터베이스처럼 기술 역할별로 층을 쌓는 스타일이다. 요청은 위에서 아래로 흐른다. 화면이 요청을 받으면 비즈니스 층이 규칙을 적용하고, 퍼시스턴스 층이 데이터베이스를 읽고 쓴다. 마틴 파울러도 프레젠테이션, 도메인, 데이터 층으로 나누는 방식을 가장 흔한 모듈화 방법 중 하나로 소개한다.

서점의 주문 흐름을 레이어드로 쓰면 대략 이렇다.

// presentation/orderController.ts
export function placeOrder(req: OrderRequest) {
  return orderService.placeOrder(req.userId, req.bookId);
}

// business/orderService.ts
export function placeOrder(userId: string, bookId: string) {
  const book = bookRepository.find(bookId);
  const total = book.price;
  return orderRepository.save(userId, bookId, total);
}

// persistence/orderRepository.ts
export function save(userId: string, bookId: string, total: number) {
  return db.execute("INSERT INTO orders ...", [userId, bookId, total]);
}

닫힌 층과 열린 층

각 층이 바로 아래 층만 호출하도록 막은 층을 닫힌 층이라고 한다. 닫힌 층은 결합도를 낮춘다. 퍼시스턴스 층의 구현을 바꿔도 프레젠테이션 층은 영향을 받지 않는다. 화면 코드가 SQL을 직접 알지 못하기 때문이다.

반대로 층을 건너뛰어 아래 층을 바로 부를 수 있게 열어 둔 층을 열린 층이라고 한다. 리처즈와 포드는 공용 유틸리티를 모아 둔 서비스 층처럼, 꼭 거칠 필요가 없는 층을 열린 층으로 두는 예를 든다.

아키텍처 싱크홀

닫힌 층의 대가가 아키텍처 싱크홀이다. 싱크홀은 요청이 아무 로직 없이 층을 그냥 통과하기만 하는 현상을 말한다. 예를 들어 책 상세 조회는 비즈니스 규칙이 하나도 없다.

// business/bookService.ts
export function getBook(bookId: string) {
  return bookRepository.find(bookId); // 아래 층에 그대로 넘기기만 한다
}

리처즈의 『Software Architecture Patterns』(O'Reilly)는 이런 통과 요청이 어느 정도 있는 건 자연스럽고, 대부분의 요청이 통과만 한다면 레이어드가 맞지 않는 신호로 보라고 한다. 그때 쓸 수 있는 대응이 층을 여는 것이다. 화면이 퍼시스턴스를 바로 부르게 하면 싱크홀은 줄지만, 화면이 데이터 접근 코드를 알게 되어 결합도가 높아진다. 수업에서 강조한 점은 이 둘이 맞바꾸는 관계라는 것이다. 싱크홀을 없애면 결합이 늘고, 결합을 막으면 싱크홀이 남는다.

모듈러 모놀리스: 업무 영역으로 칸을 나눈다

모듈러 모놀리스는 배포 단위는 하나로 두고, 코드를 카탈로그, 주문, 쿠폰처럼 업무 영역별 모듈로 나누는 스타일이다. 각 모듈 안에는 다시 작은 기술 층을 둘 수 있다. 큰 건물을 층 대신 칸으로 나누고, 칸마다 작은 계단을 둔 모양이다.

핵심 규칙은 하나다. 모듈끼리는 내부 코드와 데이터를 숨기고 공개 함수로만 소통한다.

// modules/coupon/index.ts  (쿠폰 모듈이 밖으로 내놓는 유일한 입구)
import { couponRepository } from "./repository"; // 모듈 안에서만 쓰고 export 하지 않는다
import { applyCoupon } from "./rules";

export function discountedPrice(code: string | undefined, price: number): number {
  const coupon = code ? couponRepository.find(code) : undefined;
  return coupon ? applyCoupon(coupon, price) : price;
}

// modules/order/service.ts
import * as catalog from "../catalog";
import * as coupon from "../coupon";
import { orderRepository } from "./repository";

export function placeOrder(userId: string, bookId: string, couponCode?: string) {
  const book = catalog.getBook(bookId);
  const total = coupon.discountedPrice(couponCode, book.price);
  return orderRepository.save(userId, bookId, total);
}

주문 모듈은 쿠폰 모듈의 index.ts가 내보낸 함수만 쓰고, couponRepository나 쿠폰 테이블을 직접 건드리지 않는다. 쿠폰 규칙이 바뀌어도 변경은 쿠폰 모듈 안에 모인다.

경계는 저절로 지켜지지 않는다

모듈러 모놀리스의 약점은 경계가 코드 규율에만 기대고 있다는 점이다. 한 프로세스 안에서는 import { couponRepository } from "../coupon/repository"처럼 다른 모듈의 내부 파일을 바로 import 하는 데 아무 장벽이 없다. ESLint의 import 제한 규칙 같은 도구로 막지 않는 한 그렇다. 마감에 쫓기면 누군가 쿠폰 테이블을 주문 쿼리에서 바로 조인하고, 그 순간 경계가 무너진다.

실제 사례가 Shopify다. Shopify 엔지니어링 블로그의 2019년 글 「Deconstructing the Monolith」에서 Kirsten Westeinde는 배포 단위를 늘리지 않고 모듈성을 높이려고 모놀리스를 주문, 배송, 재고, 결제 같은 실제 업무 개념 기준의 컴포넌트로 재편했다고 설명한다. 그리고 컴포넌트 사이의 비공개 코드 호출과 데이터 결합을 추적하는 사내 도구 Wedge를 따로 만들었다. 경계를 지키려면 사람의 다짐보다 도구가 필요하다는 뜻으로 읽었다.

마이크로커널: 코어에 플러그인을 끼운다

마이크로커널은 최소한의 코어에 플러그인을 끼우거나 빼며 기능을 확장하는 스타일이다. 플러그인 아키텍처라고도 부른다. 운영체제의 마이크로커널에서 이름을 따왔고, 애플리케이션 수준에서는 IDE나 브라우저의 확장 기능 구조를 떠올리면 된다.

수업의 구현은 레지스트리 방식이었다. 플러그인이 스스로 레지스트리에 등록하고, 코어는 레지스트리만 돌 뿐 어떤 플러그인이 있는지 모른다.

// core/pricing.ts  (코어: 플러그인의 존재를 모른다)
export type PriceRule = (order: Order, price: number) => number;

const rules: PriceRule[] = [];

export function register(rule: PriceRule): void {
  rules.push(rule);
}

export function finalPrice(order: Order): number {
  return rules.reduce((price, rule) => rule(order, price), order.basePrice);
}

// plugins/couponDiscount.ts  (쿠폰 기능은 이 파일 하나)
import { register } from "../core/pricing";

register((order, price) =>
  order.couponCode === "WELCOME10" ? Math.floor(price * 0.9) : price,
);

예제는 짧게 보이려고 쿠폰 코드를 플러그인 안에 박아 두었지만, 실제로는 플러그인 안에서 쿠폰 저장소를 읽어도 수정 파일은 여전히 플러그인 하나다. 쿠폰을 끄고 싶으면 플러그인 파일을 빼면 된다. 코어가 시작할 때 plugins/ 폴더의 모듈을 모두 불러오는 로더가 있다는 전제다. 로더가 플러그인 파일을 import 하는 순간 파일 맨 위의 register(...) 호출이 실행되어 레지스트리에 규칙이 등록된다. 고객사나 상품마다 할인 규칙이 다른 서비스라면 규칙마다 플러그인을 하나씩 두는 식으로 다르게 적용하기 좋다.

대가는 코어와 플러그인 사이의 약속, 즉 PriceRule이라는 함수 타입 (order, price) => number에 있다. 예를 들어 해외 판매를 시작하면서 가격을 숫자 대신 금액과 통화를 담은 Money 객체로 바꾸면, price * 0.9처럼 가격을 숫자로 계산하던 모든 플러그인을 함께 고쳐야 한다. TypeScript라면 타입이 맞지 않게 된 플러그인을 컴파일러가 짚어 주지만, 고치는 일 자체는 줄지 않는다. 플러그인이 많을수록 약속을 바꾸기가 어려워진다.

반대로 모든 변경이 플러그인을 깨뜨리는 건 아니다. TypeScript는 인자가 더 적은 함수를 인자가 더 많은 함수 타입에 그대로 넣을 수 있게 해 준다. 그래서 PriceRule 맨 뒤에 회원 등급 같은 인자를 하나 더하는 변경은 기존 플러그인을 고치지 않아도 컴파일되고, 코어의 호출부만 바꾸면 된다. 약속을 바꿀 때는 뒤에 덧붙이는 변경인지, 기존 인자의 모양이나 의미를 바꾸는 변경인지부터 구분해야 한다.

쿠폰 하나로 비교한 세 스타일의 변경 범위

같은 쿠폰 할인 기능을 세 스타일에 넣었을 때 고친 곳은 다음 표와 같다. 수업 예제 코드 기준이고, 세는 범위가 스타일마다 조금 달라서 먼저 기준을 밝혀 둔다.

  • 레이어드: 쿠폰 코드를 받는 화면 파일까지 센다.
  • 모듈러 모놀리스, 마이크로커널: 주문 요청에 쿠폰 코드가 이미 실려 온다고 보고 화면 쪽 수정은 세지 않는다. 쿠폰 모듈은 안에서 파일이 몇 개로 나뉘어도 새 폴더 하나로 센다. 마이크로커널은 plugins/ 폴더를 읽는 로더가 코어에 이미 있다고 본다.
  • 화면 파일까지 똑같이 세면: 레이어드 3, 모듈러 모놀리스 3, 마이크로커널 2가 된다. 차이는 줄지만, 쿠폰 규칙이 한곳에 모이느냐 여러 층에 흩어지느냐의 차이는 그대로 남는다.

실제 프로젝트라면 여기에 테스트와 설정 파일이 더해진다.

스타일 분할 기준 쿠폰 추가 시 수정 파일 변경이 모이는 곳 주된 대가
레이어드 기술 역할 3개 (화면, 서비스, 저장소) 여러 층에 흩어짐 싱크홀, 기능 하나가 모든 층을 지나감
모듈러 모놀리스 업무 영역 2곳 (새 쿠폰 모듈, 주문 모듈의 호출부) 쿠폰 도메인 안 경계를 지키는 규율과 도구
마이크로커널 코어와 플러그인 1개 (쿠폰 플러그인) 플러그인 파일 하나 코어와 플러그인 약속 변경 비용

레이어드에서는 쿠폰 코드를 받을 화면, 할인을 계산할 서비스, 쿠폰을 읽을 저장소를 모두 고친다. 기능은 하나인데 층마다 한 조각씩 손대야 한다.

// presentation/orderController.ts: 쿠폰 코드를 받아 넘긴다
return orderService.placeOrder(req.userId, req.bookId, req.couponCode);

// business/orderService.ts: 할인을 계산한다
const coupon = couponCode ? couponRepository.find(couponCode) : undefined;
const total = coupon ? applyCoupon(coupon, book.price) : book.price;

// persistence/couponRepository.ts: 쿠폰을 읽는다
export function find(code: string) {
  return db.queryOne("SELECT * FROM coupons WHERE code = ?", [code]);
}

모듈러 모놀리스에서는 쿠폰 모듈을 새로 만들고 주문 모듈에서 공개 함수를 부르는 한 줄만 더한다. 마이크로커널에서는 플러그인 파일 하나를 추가하면 코어는 그대로다.

파일 수가 적다고 늘 이기는 건 아니다

표만 보면 마이크로커널이 가장 좋아 보이지만, 수업이 말한 결론은 반대 방향이었다. 파일 수는 "무엇이 바뀌는가"에 대한 답일 뿐이다. 바뀌는 대상이 달라지면 순위도 뒤집힌다.

  • 모든 화면에 공통 로그를 남기는 변경이라면 레이어드가 유리하다. 프레젠테이션 층 한 곳만 보면 된다. 도메인별 모듈에서는 모듈마다 손대야 한다.
  • 가격의 모양을 바꾸는 변경(숫자에서 Money 객체로)이라면 마이크로커널이 가장 비싸다. 모든 플러그인을 고쳐야 한다.
  • 쿠폰 팀과 주문 팀이 따로 있는 조직이라면 모듈러 모놀리스가 팀 경계와 코드 경계를 맞춰 준다.

어떤 스타일을 고를까

스타일을 고를 때 나는 수업에서 받은 세 가지 질문을 체크리스트로 쓰기로 했다.

  1. 무엇이 자주 바뀌나? 기술 기반(화면 프레임워크, DB)이 자주 바뀌면 레이어드, 업무 규칙이 도메인별로 바뀌면 모듈러 모놀리스가 맞다.
  2. 팀이 어떻게 나뉘나? 프론트엔드, 백엔드, DBA처럼 기술로 나뉜 팀은 레이어드와, 도메인별 팀은 모듈러 모놀리스와 잘 맞는다.
  3. 기능을 탈부착해야 하나? 고객사마다 켜고 끄는 기능, 자주 늘어나는 규칙이 있으면 마이크로커널을 고려한다.

세 스타일은 섞어 쓸 수 있다. 서점 전체는 모듈러 모놀리스로 나누고, 할인 규칙이 계속 늘어나는 쿠폰 모듈 안에서만 마이크로커널을 쓰고, 각 모듈 내부는 작은 레이어드로 짜는 식이다. 실제로 이 조합이 수업 예제에서 가장 현실적이라고 느꼈다.

아직 쪼갤 기준이 분명하지 않다면 하나의 모놀리스에서 시작하는 것도 방법이다. 마틴 파울러는 MonolithFirst에서 도메인 경계를 충분히 이해하기 전에 처음부터 서비스로 나누면 경계를 잘못 긋기 쉽다고 지적한다. 모듈러 모놀리스는 경계를 미리 연습해 보는 자리로도 쓸 수 있다.

자주 묻는 질문

모듈러 모놀리스와 마이크로서비스는 무엇이 다른가요?

모듈러 모놀리스는 도메인별로 나뉜 모듈을 하나의 단위로 배포하고, 모듈끼리는 같은 프로세스 안에서 함수로 호출한다. 마이크로서비스는 각 도메인을 따로 배포하고 네트워크로 호출한다. 그래서 마이크로서비스는 독립 배포와 확장이 쉬운 대신 네트워크 지연과 장애를 감당해야 한다. 분산 스타일은 시리즈 2편에서 다룬다.

아키텍처 싱크홀은 무조건 나쁜가요?

아니다. 단순 조회처럼 로직 없이 통과하는 요청은 어느 정도 생기기 마련이다. 문제는 대부분의 요청이 통과만 할 때다. 그 비율이 높다면 층을 일부 열거나, 레이어드가 이 시스템에 맞는 스타일인지 다시 볼 신호다.

마이크로커널의 플러그인 약속은 어떻게 덜 깨지게 하나요?

새 정보는 맨 뒤 인자나 order 같은 문맥 객체의 새 필드로 덧붙이면 기존 플러그인이 그대로 동작한다. 깨지는 건 기존 인자의 타입이나 의미를 바꿀 때다. 그래서 약속은 처음부터 작게 잡고, 바꿀 때는 기존 모양을 유지한 채 덧붙이는 방향을 먼저 찾는 편이 낫다.

정리

세 스타일은 같은 질문에 다르게 답한다. 레이어드는 기술 역할로, 모듈러 모놀리스는 업무 영역으로, 마이크로커널은 코어와 확장으로 시스템을 자른다. 쿠폰 예제에서 수정 파일이 3개, 2개, 1개로 줄었지만, 그건 쿠폰이라는 변경에 대한 답이다. 다른 변경을 놓으면 순위가 바뀐다. 그래서 아키텍처 스타일은 정답 하나를 고르는 일이 아니라 프로젝트의 품질 요구사항과 상황에 맞춰 트레이드오프를 고르는 일이다.

다음 편에서는 배포 단위를 여러 개로 나누는 분산 아키텍처 다섯 가지와, 서비스를 여러 번 거칠수록 꼬리 지연이 커지는 이유를 TypeScript 시뮬레이션으로 확인한다.
